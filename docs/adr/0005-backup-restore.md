# ADR 0005: Complete, portable backup and transactional restore

- Status: Accepted
- Date: 2026-10-04
- Updated: 2026-10-13

## Version 5 durability additions

Version 5 includes the global restore epoch, practice draft revisions and run identities, writing draft CAS revisions, immutable submission receipts and processing leases, frozen mock exam sessions, and cumulative vocabulary time segments. A successful restore rotates the epoch inside the replacement transaction, advances restored draft/session revisions, releases mock writer leases, pauses active exams, and marks incomplete submission tasks retryable with their original IDs. Failed restores retain the old epoch. Completed submissions and historical grades are preserved; no IDs or scores are invented for old history.

Complete v1–v4 backups receive empty durability tables and a fresh initial epoch before strict validation. Version 5 requires all six additions, validates receipt hashes and result associations, validates frozen PDF/audio references, and rejects malformed sessions. See [ADR 0007](0007-durable-learning-sessions.md).

## Version 4 snapshot (retained compatibility contract)

The JSON format identifies itself as `ielts-studio`, version `4`, with `exportedAt`, `data`, and `files`. It snapshots every initialized application table, including vocabulary courses/catalog and sense targets, source and grading context, study preferences and heartbeat ledger, import previews, fixed assessment assignments and unfinished inputs, learning state, active sessions, raw review details, immutable grading audit, supplemental context attempts, target introductions and minute steps, persistent term/target dispositions and operation idempotency records, FSRS state, practice drafts, dictation history, and writing revisions. Imported material bytes travel in a base64 manifest. The AI provider key is stored separately in `ai-provider.secret.json`; JSON and raw database exports exclude it, and restore does not overwrite it.

Version 4 requires all current tables and every column in each row. Unknown or omitted fields/tables, invalid scalars or JSON, malformed vocabulary state, unsupported ratings/modes, invalid attachment manifests, and dangling database foreign keys are rejected. Vocabulary current drafts are checked structurally, including exercise and frozen target snapshots, requested rating, rating source, audio playback state, supplemental flags/counter and consolidation event; at most one session and one assessment may be active. Audit ratings must agree with their durable review record. Catalog links and exercise/course associations are validated. Finished assessment results are recomputed from their immutable assignment and saved answers solely for validation. SQL constraints provide the final duplicate-ID and foreign-key checks inside the replacement transaction.

Supplemental attempts are a separate immutable ledger, never scheduled reviews. Their word/session/course references, unique submission IDs across both ledgers, dates, duration, exact published exercise and target span, and private source SHA/Passage ranges are validated. Objective correctness, typo eligibility, decision reason and effective audit rating must agree with the frozen accepted answers and original input; validation never substitutes the currently edited term or exercise. Typo confirmation retains `correct: 0`. Restore preserves the attempt's observed next-due timestamp without replaying FSRS or deriving a new interval.

Targets have stable identities, explicit versions, meanings, level evidence and course memberships. Membership exercise IDs must belong to the same entry and target; every published membership retains at least two distinct published examples. A frozen target in a Practice Attempt is structurally and referentially checked without substituting today's edited meaning, level or version. A target-state row must reference an existing catalog definition, including definitions now held as draft, and its normalized term. A non-null personal word reference must have that same normalized term; it cannot attach another word's progress. A deleted or renamed personal word may leave its target state with a null word reference. Step 1/2 requires an introduction timestamp and a valid minute due date; step 0/3 has no minute due date. A non-null last submission must point to the same frozen consolidation event in either the scheduled or auxiliary ledger, at an older state version. A merged event has one scheduled grade; it does not create a second auxiliary row. Analytics preserves detached introductions as history but excludes minute steps without an available personal word from the pending/due queue counts.

Persistent self-reported known targets and paused whole terms retain their exact flags and versions. The operation ledger validates each UUID, action and strict original request payload, including target or introduction word/session references. Restoration never executes these requests, turns self-report into objective correctness, or creates a rating. Study preferences preserve focus, next level, policy version and private catalog registration key. Unknown optional target fields on old active cards remain absent.

## Explicit version 1, 2 and 3 migration

Only the known complete IELTS Studio version 1 format is accepted. Before applying the same strict validation, migration adds absent `vocabulary_learning_state`, `vocabulary_sessions`, and `vocabulary_review_audit` as empty arrays. It also retains the previously supported additive migration for a missing `practice_sets.resource_json`, setting it to `{}`. No other missing old table or column is filled in. Upstream ISTS partial exports and arbitrary older schemas are not complete Studio backups.

For complete version 1 or 2 snapshots, the ten v3 additions are initialized as empty arrays: courses, catalog entries, catalog links, review context, word context, study preferences, study heartbeats, import previews, assessments, and supplemental attempts. Existing session JSON gains only absent `courseId: null`, `current.exercise: null`, `current.requestedRating: null`, `current.ratingSource: automatic`, `current.supplemental: false`, `current.canSupplement: false`, and `supplementalReviewed: 0`. These are compatibility values for an active draft, not invented historical grading or provenance. Export applies these same defaults to its cloned legacy session JSON without changing the on-disk row. Version 2 still requires every v2 table and old column; version 3 never receives these migration defaults. Initialization creates schema only and does not install a public or private catalog during restore.

Complete v1/v2/v3 snapshots additionally initialize the three v4 tables as empty arrays: target state, term dispositions and target operations. Existing study-preference rows gain only absent `focus: general`, `next_level: B2`, `policy_version: 1` and `private_catalog_key: null`. Existing catalog entries gain only absent `targets: []`. These defaults retain the old session mode and do not infer past sense introductions, CEFR levels, minute events or known/pause decisions. Version 3 still requires all ten v3 tables and their old columns. Version 4 receives no migration defaults during validation. A v4 export applies documented defaults to cloned legacy rows only; raw historical exercise JSON, answers, FSRS state and old dates stay unchanged.

After replacement, vocabulary initialization annotates legacy learning state using the earliest historical review, or the original creation date for words with positive repetitions. It does not reschedule cards, alter raw correctness or ratings, replay FSRS during restore, or change old FSRS rows. The audit for old reviews remains absent/unknown; current word text must never be substituted for an unknown historical standard answer. Version 1 has no active vocabulary session to resume unless the known new tables were explicitly present in that snapshot. Validation clones its input before migration and does not mutate the caller's snapshot.

## Portable attachments

Attachment references use `upload:<materialId>`. Original absolute paths and directory traversal are not accepted on restore. The importer generates fresh UUID filenames inside the configured upload directory and retains display filenames. Export resolves symlinks before reading files to ensure they belong to that directory. Official resource references must resolve to an included material and its attachment bytes. Attached bytes are limited to 256 MB; larger libraries require a copy of the entire stopped application's data directory.

Reading exercise provenance additionally requires the referenced material, a matching SHA256 of its included bytes, a known reading Passage and an allowed PDF page range including any final page. The quote must equal the stored sentence and match its character span length. This verifies linkage and snapshot consistency; it does not run OCR or reconstruct PDF text during restore.

Private vocabulary-list provenance uses the existing stable `/api/uploads/<materialId>` reference rather than a local filename. The source material must be a PDF with included bytes matching its source SHA256; page and original quote are required by the target schema. These references are checked in catalog definitions and frozen current/historical target snapshots. Restoring to a fresh UUID filename therefore does not break provenance. The user-supplied PDF and its extracted list remain local and are not committed to Git. Validation checks linkage and integrity, not the source dictionary's semantic quality or any official IELTS syllabus identity.

An exercise snapshot has either both catalog entry and course IDs, or neither for a personal sentence. A catalog review's course must match its frozen exercise provenance. The original entry and course must still exist, but a later package withdrawal may change their current membership; validation does not substitute that current association for historical provenance. Live target memberships remain strict subsets of the current entry's course IDs, including archived definitions held as draft. A personal sentence has no catalog provenance, while its review context may retain the valid course selected during that session. Restore preserves these distinct fields without assigning a course to the personal source or rewriting history.

## Restore safety and session continuity

Before replacement, save a complete current JSON snapshot under the database directory's `backups` folder. If existing attachments are missing, outside the upload directory, not files, or exceed the limit, save a synchronous SQLite snapshot instead and return an explicit warning. This permits a healthy backup to repair missing media. Unknown failures still abort. The fallback SQLite snapshot contains only the database, so original attachments are retained alongside it.

Write imported attachments into new files, then replace tables in one synchronous SQLite transaction. Save the current vocabulary session revisions before deleting rows. After inserting the snapshot, set each restored revision to `max(restoredRevision, previousLocalRevisionForSameId ?? 0) + 2` and update its timestamp. The two-step increase distinguishes restore from a single checkpoint acknowledgement, which increases the revision by one; an old browser draft therefore cannot mistake a restore for a lost save response. Preserve status, mode, current card and typed draft, skipped IDs, learned/reviewed/supplemental counters, and submission association. A target card's existing `restoreVersion` is updated to the new preference token; its sense, exercise, target-state version, minute event, original start time and input remain identical. Cards without that optional protocol field do not have target metadata invented. A restored active session can continue after fetching its new revision; it is not ended as a side effect of restore. Selection prioritizes an active session over ended sessions regardless of snapshot insertion order or their timestamps. Old pages and repeated restores cannot reuse the previous write token.

Foreign-key enforcement is temporarily disabled only around the synchronous replacement and checked before commit. Any SQL constraint or foreign-key failure rolls back all rows, including session revisions, and cleans newly staged attachments. Original attachments remain available for recovery. Enforcement is restored in `finally`.

Import-preview and assessment revisions receive the same `max(restored, priorSameId) + 2` treatment. Active assessment questions, input, position and completion status remain unchanged. Older pages cannot confirm an obsolete preview or overwrite restored assessment input.

The study preference row carries a positive, safe-integer `restore_version` token. Versions 3 and 4 require the field explicitly. Its restored token becomes `max(previousLocalToken ?? 1, snapshotToken ?? 1) + 2` in the same replacement transaction, retaining headroom for another token change. Heartbeat, preference and target-operation writes must present the current token before writing any time, ledger entry or setting, so a request already in transit cannot alter restored state. The token change rolls back with all other rows on failure.

Legacy version 1/2 validation still introduces the study-preference table as an empty array. After replacement, an absent preference row is initialized with the new token, a 900-second goal, pause off, start rank 1, general focus, B2 next level, policy version 1 and a null private catalog key. Academic is selected only if that course exists in the restored snapshot; otherwise the selection is null. An old backup without courses therefore leaves new catalog learning suspended until the user selects a course, while existing due reviews and learning history remain available. Existing preferences retain their selected course, goal, pause, rank and known policy fields; only the restore token changes. Initializing the missing row prevents a default token of 1 from accepting an old page's requests.

Import previews include explicit ready/pending counts. Newly imported content is a draft until reviewed; existing catalog content is reused without replacement. Confirmation stores its original course ID and result in the preview transaction. Retrying the same confirmation revision and title returns that saved result even if the first response was lost. Restore advances the revision and prevents an old confirmation token from being reused. Assessment continuation prioritizes the active record rather than SQLite insertion order, so changing snapshot row order cannot hide an unfinished test.

On successful restore, Settings removes `ielts-studio-writing-recovery`, `ielts-studio-vocabulary-recovery`, `ielts-studio-vocabulary-assessment`, and `ielts-studio-vocabulary-study` from browser storage, dispatches `studio:backup-restored`, and sends `{ type: 'studio:backup-restored' }` through `BroadcastChannel('ielts-studio-restores')` when available. Other vocabulary pages discard their old recovery draft and reload server state. Browser storage/channel failures do not undo a committed restore: server-side vocabulary revision checks still reject stale writes. Clearing the writing cache prevents that cache from being replayed on a new mount; it does not pause an already-open writing page's autosave. Close active writing pages before replacing the database.

The optional raw `.db` export uses SQLite's backup API, preserving committed WAL data. It is not a complete media backup. Tests reopen its bytes to check database integrity and foreign-key consistency.

## Regression coverage

Isolated temporary databases verify version 4 table/attachment round trips, strict known version 1/2/3 migration, raw-history preservation, rejection of omitted old fields, active-session and assessment continuation with new revisions and reordered rows, supplemental raw errors and frozen sense snapshots after catalog edits, malformed auxiliary/target scalar, reference, minute event and operation payload rejection, reading and private vocabulary source SHA associations, failed-restore rollback and staged-file cleanup, large audio manifests, missing-media repair, and exclusion of provider secrets. Browser notification tests verify all cache keys and graceful operation when storage or BroadcastChannel is unavailable. Analytics reads do not initialize or mutate state: word/target introductions use only explicit timestamps; formal grading accuracy uses only the original review ledger; minute and extra-sentence auxiliary accuracy is separate; merged events count once as formal grades; self-reported known and whole-term pauses never become measured mastery or accuracy samples. Completed assessment recommendations are checked against their frozen questions and saved answers; unknown historical results and auxiliary purpose stay unknown.
